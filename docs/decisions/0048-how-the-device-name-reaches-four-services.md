# ADR-0048 — How the device name reaches four services

**Status:** Proposed — the *what* is settled; this is the *how*, and one part
of it (nothing is applied while the device is running) is a decision rather
than a detail.
**Date:** 2026-09-20
**Raised by:** Phase 9 subphase 9e, implementing
[ADR-0022](0022-settings.md)'s 2026-09-20 amendment
**Implements:** ADR-0022 §2 (one name for every renderer) and §3 (renaming
requires a restart)
**Relates to:** [ADR-0035](0035-settings-api.md) (one registry, one generic
API, a row is wired when something reads it), [ADR-0044](0044-settings-row-vocabulary.md)
(`secret`, `placeholder`, and the text row that takes this name)

## Context

ADR-0022 §3 closed its own Unverified section by measurement: **nothing
propagates.** The four names agree because each was set to the same literal
at build time.

| what | where its name lives today |
|---|---|
| LMS player | `squeezelite.service` — `-n gexis` **inside `ExecStart`** |
| Spotify | `/var/lib/go-librespot/config.yml` — `device_name: gexis` |
| Bluetooth | `/etc/bluetooth/main.conf` — `Name = gexis`, and the adapter alias |
| mDNS | the system hostname |

Three of the four are files this image already owns. The fourth is an
argument baked into a unit's command line, which is the one that decides the
shape of the rest.

## Decision

### 1. `squeezelite.service` reads the name from a file, and the daemon writes that file

The unit becomes `-n ${GEXIS_DEVICE_NAME}` with
`EnvironmentFile=-/etc/gexis/device-name.env` and a fallback, and the daemon
writes that one file.

Rejected: **a systemd drop-in generated by the daemon.** Overriding
`ExecStart` requires restating the whole command line, so the drop-in would
hold a second copy of the unit's arguments — mixer device, volume control,
output — and drift from the image's copy the first time either changed. The
name is the only part that varies, so the name is the only part that should
live outside the unit.

Rejected: **rewriting `squeezelite.service` in place.** The image ships it;
a daemon editing a shipped unit means the next build silently reverts the
device, and the difference is invisible until someone wonders why the rename
came back.

**The env file is the image's interface for this**, so the image ships it
with the build-time name rather than leaving the unit to fall back.

### 2. Nothing is applied while the device is running

Not the hostname, not the Bluetooth alias, though both *can* be set live.

ADR-0022's Unverified section worried that *"the user renaming the device
from a remote browser may disconnect themselves"*. Setting the hostname live
does exactly that: `gexis.local` stops resolving the moment it lands, and the
phone that just typed the new name is the thing that loses its way back.

Applying two of four immediately would also make the rename **partly** true —
the panel advertising one name over Bluetooth and another over LMS until the
next restart, which is a state nobody asked for and nobody can explain.

**So all four are written and none takes effect until a restart**, which is
what George ruled and what the row says. The `reboot` row added in 9d is the
obvious way to take it.

The row carries `restart: true`, and the panel's confirmation reads *"saved —
restart to use it"* rather than *"saved"*. **This is not an eighth mechanic**
(ADR-0044): it changes no behaviour of the row, only the wording of the
sentence that follows a write, and it exists because a silent "saved" on a
deferred setting is the one message that is actively wrong.

### 3. All four are attempted, and the answer says which landed

ADR-0022: *"four writes that must all land before the restart."* They are
independent files and any one can fail — a read-only mount, a missing
`bluetoothctl`, a config file an update replaced.

**The write is not reported as successful unless every target took it**, and
a partial result names the ones that did not. The alternative — a single
boolean — leaves a device half-renamed with nothing on screen to say so, and
the failure only surfaces at the restart, when the cause is hours behind.

### 4. The hostname is sanitised; the three display names are verbatim

The sanitiser is the one the design specifies and the panel already carries:
fold accents, lowercase, anything outside `[a-z0-9-]` to a hyphen, trim
hyphens, cap at 63, and fall back to `gexis` if nothing survives.

`Gexis Living Room` therefore advertises as that over LMS, Spotify and
Bluetooth, and resolves at `gexis-living-room.local`. ADR-0022 requires the
user to see both, which is what the header does.

### 5. The header reads name · hostname · address, from the daemon

The IP is not derivable in the panel and the hostname must be the system's
own rather than the panel's guess at it — after a rename they disagree, and
that disagreement is the thing the user needs to see.

`GET /settings` gains a `device` object beside `groups`: the stored name, the
live hostname, and the address. One fetch, already refetched on every
revision bump, and no new route.

**The address is found by asking the routing table, not by resolving our own
hostname**: a UDP socket "connected" to a documentation address sends nothing
and reports the interface that would carry it. `gethostbyname(gethostname())`
answers `127.0.1.1` on a Debian-derived image, which is true and useless.

## Consequences

- **The gate needs a restart to pass**, by construction: rename, restart,
  then confirm all four advertise it. Nothing can be checked before the
  restart except that the four files changed.
- **Renaming to something that sanitises to nothing** (`"***"`) gives the
  hostname `gexis` while the display names keep the string. That is the
  design's fallback, and the header shows both, so it is visible rather than
  surprising.
- **The running device needs the new `squeezelite.service`** before the
  LMS name can move at all. Until the next image build that is a file
  deployed by hand, like the daemon and the UI.
- **A rename is now the one setting that changes how the device is reached.**
  George develops against `gexis`, deliberately: *"For development purposes I
  will always keep it called gexis though."*
- **`device_name` becomes wired** in ADR-0035's sense, and the first wired
  row whose effect is deferred. The toast has to say so; a silent success
  would read as "done" when nothing has changed yet.

## Open

- **The warning text is Design Claude's** and has not arrived. George,
  2026-09-20: *"Changing device name will require a restart. We need to make
  it clear in the design. Maybe under the form of a text warning."* The note
  shipped here is a placeholder that says the true thing plainly.
- **Whether `warn` should extend to a text row.** It is choice-only today
  (ADR-0044 §2) and this is the first text row with a consequence worth
  holding back. Not extended here: one use is not a mechanic.
- **Whether a rename should offer the restart.** The `reboot` row is two
  categories away in Device, so the two are at least on the same screen.
