# ADR-0105 — Updates over the network

**Status:** **Accepted** — George, 2026-09-29, the four decisions below
(each marked **Decided**). Decision 2 is accepted subject to its prototype:
the tested set's size and upkeep are measured first, and the record amended
with the numbers.
**Date:** 2026-09-29
**Phase:** 13c ([DEVELOPMENT.md](../DEVELOPMENT.md)). The first public release
waits on it (George, 2026-09-29: *"13a, b and c all needed before release"*).
**Builds on:** [ADR-0021](0021-deployment-flashable-image.md) *"Updates are
in-place package updates"* (2026-09-05), which decided the shape and specified
none of the machinery. **Shares with:** [ADR-0106](0106-plugins-you-install-and-update.md)
(13a) the signed repository and the idea of a tested set.

## What ADR-0021 already decided

No reflashing for an update; no A/B partitions; a signed repository we host;
settings, pairings and network kept on the writable root; `alsa-lib` pinned and
held; the `output` definition a packaged file with a known checksum; each build
recording what it pinned. **None of it exists today.** The image-build stages
copy our files straight into the root filesystem, so a device can only move
forward by being reflashed.

## Proposed

### 1. Our parts become Debian packages, and the image is built from them

| Package | What it carries |
|---|---|
| `gexis-core` | the core and its Python environment (arm64) |
| `gexis-ui` | the panel's and phone's built pages |
| `gexis-system` | our units, ALSA files, scripts, splash, `notices.json`, `verify` data |
| `gexis-skins` | Gelo5's corpus and the animated packs (large, changes rarely) |
| `gexis-player` | depends on exact versions of the four above: **the release** |

**The image installs these packages**, so what a new card starts from and what
an update brings are the same bytes. `make image` builds the packages first,
then the image from them. `verify-image.sh` keeps working, against the
installed package contents.

### 2. A signed repository we host

A static apt repository (generated by `reprepro` or `aptly`) served over HTTPS,
**GitHub Pages being the candidate** (free, versioned, already where the code
is). Signed with a key of our own; the image trusts that key for our packages
only (`signed-by=` in its source line). **Decision 1, who holds the signing
key** - George, offline, with Claude asking for each release signature; or a
key on R2D2 that Claude signs with. *Recommendation was George offline.*
**Decided: the key lives on R2D2** (George: *"Key on r2d2"*), and Claude signs
releases with it. **What that means, written down so it stays true:** anyone
who gets R2D2's key can publish an update every device will install, so R2D2
becomes part of every device's trust. Kept to as small a surface as possible:
a key used **only** for signing the repository (a signing subkey, not an
identity key), its **revocation certificate and a backup of the primary key
made at creation and kept off R2D2 by George**, and the key's fingerprint in
the image so a replacement is a deliberate release, not a silent swap.

### 3. The operating system's own packages — **Decided: a tested set**

The device also runs Raspberry Pi OS and Debian, which move on their own.

- **(a) As they come**, with `alsa-lib` and whatever else we pin held.
  Cheap, and security fixes arrive at once. The device's package set drifts
  from anything we tested; ADR-0021 accepted that drift but named the audio
  chain as the thing to protect.
- **(b) A tested set.** Each release names the exact versions of every package
  it was tested with, and the device installs those and nothing newer until
  the next release. George's rule for plugins (*"we need to check them before
  allowing an update"*) applied to the whole device. **Its real cost:** the
  Raspberry Pi archive drops old versions (it dropped the pinned `alsa-lib` on
  2026-09-12, which failed a build), so a tested set has to be **kept
  downloadable by us** - a copy of every package a release depends on, in our
  repository. Debian has `snapshot.debian.org`; whether the Raspberry Pi archive
  has an equivalent is **not established**.
- **(c) Between the two**: Debian's security updates as they come (held
  packages excepted), everything else only with a release.

*Recommendation: (b), because the product's claim is a sound path you can
check, and (a) makes every device a different machine a week after its update.*
**Decided: (b), a tested set** (George: *"Fine"*). **Its storage and effort
are measured in a prototype first**, and this record is amended with the
numbers before the repository is built around it.

### 4. How an update happens on the device

1. **Check** the repository (daily, or *Check now*).
2. **Download everything first**, into `/var/cache/gexis/updates/`. Nothing is
   touched until the whole release is on the card and verified.
3. **Back up** (ADR-0083's archive) automatically.
4. **Wait until nothing is playing**, and hold the device while updating
   (`systemd-inhibit`); the panel says *Updating* and does not take a takeover.
5. **Install**, then **check the device**: the core answers, the panel draws a
   frame, the `output` definition matches its checksum, `alsa-lib` is the
   pinned version.
6. **On failure, go back**: the previous release's packages are kept in the
   cache and reinstalled. A restart only when the kernel or firmware changed.

**Decided: yes** (George: *"ok"*) - the question was: is that enough without A/B partitions? A power cut in the middle
of step 5 can leave a card that does not boot, which A/B would survive. The
last resort is what works today: reflash, then Restore. *Recommendation: yes
for now; the audio-player failure that matters is "an update broke the sound",
which step 5-6 covers, and A/B doubles the system's footprint (ADR-0021).*

### 5. Settings move forward with the code

The settings registry gains a version. A release that adds, renames or removes
a row carries a migration the core runs at start, and the registry tests prove
each one (LESSONS 19-20: the checks that only ran in production).

### 6. What the user sees

Settings → System → **Updates**: the installed version (the row exists), *Check
now*, *Update now* when one is waiting, *What changed* (the release's notes),
and **Manual / Automatic** - the `updates` row inventoried in ADR-0022 as
[R][N]. **Decided: Manual by default** (George: *"agree"*), with the panel and
phone saying an update is waiting; Automatic, when chosen, runs at night and
never while playing. The row is confirmed; it is surfaced when the mechanism
exists.

### 7. What still needs a reflash

A new Debian release (13 → 14), a new partition layout, a new boot mechanism.
Named in the release notes when it happens; rare.

## Amendment, 2026-09-30 — the tested set, measured

[Finding 104](../findings/104-what-a-tested-set-weighs-and-where-it-can-live.md),
the prototype decision 3 asked for:

- **1,027 packages, 880 MB** of package files: 140 from Raspberry Pi (497 MB -
  Chromium, kernels, firmware), 887 from Debian (383 MB).
- **The Raspberry Pi archive indexes only the newest version**; its pool keeps
  the old files (alsa-lib's back to Debian 10), undocumented how long. Section 3
  said the archive *"dropped the pinned `alsa-lib`"*: it dropped it **from the
  index** (ADR-0021's amendment says the same), which is what makes apt unable
  to install it. **No Raspberry Pi snapshot service exists**; Debian's does.
- **GitHub Pages cannot hold it** (1 GB per site; one set is 880 MB; git
  refuses Chromium's 122 MB file). Section 2's candidate stands for nothing
  larger than our own packages. **GitHub Releases can**, per its documentation
  (no total or bandwidth limit, 2 GiB a file), but 1,000 files a release is
  fewer than the set's 1,027.

**Decision owed (George): where the tested set lives.** The signing and the
device side do not change with the answer.

## Not in this record

- **Plugins' own updates** — ADR-0106. The repository is shared.
- **How the prototype for the tested set is measured** — its first task once the
  packages exist.

## Unverified

- Whether the Raspberry Pi archive offers dated snapshots.
- How large a tested set's copy is, and whether GitHub Pages' size limits hold
  it (they are documented; not checked against a real set).
- Whether `apt` on this image can reinstall a previous version from a local
  cache cleanly in every case (held packages, removed dependencies).
